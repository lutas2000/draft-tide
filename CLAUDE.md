## Stack and toolchain

TypeScript strict (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`) with ESM sources. TypeScript is pinned to 6.0.x because typescript-eslint supports only `<6.1` (the spikes used 7). Sources import with explicit `.ts` extensions and use only erasable syntax, so Node 24 runs them directly; workspace packages export their `src/index.ts`. Dependencies are pinned to exact versions. The rest of the stack:
- Desktop: Electron with a React + Vite GUI, shadcn/ui, Tailwind and TanStack Query.
- Runtimes: the CLI and MCP server run on a **bundled Node LTS companion**, not on Electron's Node. The Engine runs there in development; release builds ship it as a **Node SEA** built from that same Node, with its own signing identifier (M1-09 packaging).
- Storage: SQLite through better-sqlite3, Zod for contracts (exported to JSON Schema, with branded IDs), and Commander for the CLI.
- Agent integration: the official MCP TypeScript SDK over stdio.
- Diffs: jsdiff.
- Remote sync: the bundled **full** Git (with `git-remote-https`) over https, GitHub sign-in through a GitHub App's device flow (user tokens with refresh, no client secret), and the token in the OS keychain. No Git library, and no backup container (yazl/yauzl are dropped).
- Build: pnpm workspace; `tsc` for type checking, Vite for the GUI, esbuild for main/preload/Engine/CLI/MCP; ESLint (typescript-eslint) and Prettier; `@electron/packager`, `@electron/fuses` and `@electron/osx-sign` called directly (the parts Electron Forge runs underneath; Forge itself fights pnpm, see `docs/compatibility.md`) with `hdiutil` for the DMG, `postject` for the Engine SEA; Changesets for versioning.
- Tests: Vitest with fast-check, integration tests against real Git, filesystem and SQLite (not mocks), and Playwright for Electron GUI E2E.

Add a dependency only when a verified feature needs it.

## Architecture: one Engine, many clients

```
React GUI → restricted preload → Electron Main ─┐
CLI  → engine-client ───────────────────────────┼─ local Engine (only writer)
MCP stdio → engine-client ──────────────────────┘    ├ core use cases / operation state machine
Skill guides external agents to CLI/MCP              ├ git-backend (the project's own repo)
                                                     ├ adapter-filesystem (scope, capture, write-back)
                                                     ├ local-store (SQLite, journal, sync queue)
                                                     ├ remote provider (GitHub sign-in, repo management)
                                                     └ preview supervisor → isolated Preview Host
```

Layout: `apps/desktop`, `apps/companion`, `packages/{contracts,core,git-backend,adapter-filesystem,local-store,remote-github,engine-client}`, `skills/draft-tide/` (`SKILL.md` and `references/reference.md`; it names tools and codes only, never a Git command, and `apps/companion/test/skill.test.ts` checks it against the catalog), `fixtures/`, `docs/`. `fixtures/` holds test-only code (the fake GitHub), never shipped. git-backend is the only package that runs Git; adapter-filesystem only reads, stages and measures the folder; remote-github is the only code that talks to GitHub's API and holds the token; core orchestrates them through ports, and neither adapter imports the other (lint enforces it). Split out a package only when publishing or isolation needs it.

**The operation catalog** (`packages/contracts/src/catalog.ts`) is the one list of Engine operations. It defines each operation's input and output schemas, whether the desktop is offered it, the tool-channel access (`always` / `agent-access` / `none`) and its effect. The Engine dispatcher, `authorize()` in core, the CLI, the MCP tools and the GUI's typed bridge all follow from it. A new operation starts there. Inputs are strict objects, so self-asserted flags (`confirmed`, `force`) are rejected as `INVALID_ARGUMENT`.

Invariants that span modules:
- **Single writer.** The Engine is the only process that writes design data or SQLite. It is started on demand, and a cross-process startup lock plus handshake keeps it to one Engine per data store. Per-project write guards serialize writes. GUI, CLI and MCP never open the DB, never run a writable core in-process, and never shell out to Git.
- **Core stays pure.** It receives ports and never imports Electron, React, the MCP SDK, better-sqlite3, providers or model SDKs.
- **Transport.** Clients use length-framed JSON over a Unix socket or Windows named pipe. There is **no HTTP control port** in production.
- **Desktop identity (macOS).** The Engine authenticates the desktop channel by code signature, not by a token file.
  - **Check.** It reads the peer's audit token (`LOCAL_PEERTOKEN`) and checks `anchor apple generic and identifier "<app id>" and certificate leaf[subject.OU] = "<team>"` plus the Developer ID markers (`certificate 1[field.1.2.840.113635.100.6.2.6] exists and certificate leaf[field.1.2.840.113635.100.6.1.13] exists`). Identifier-only can be forged with an ad-hoc signature. Team-only admits the companion Node running any script. Without the markers, same-team Apple Development builds would pass. Verified with a real Developer ID and a notarized build.
  - **Handshake.** macOS reports the socket's *last user* and computes the token at query time, so a request followed by an exec into the real app passes a one-shot check. Pin T0 (pid + pidversion) at hello, check it, send a nonce, accept the echo only from the same instance, and re-check every later message against T0.
  - **Hardening.**
    - **Companion Node.** Never ship the official Node binary as is. It carries `get-task-allow`, dyld environment variables and `disable-library-validation`, so any same-user process can take its task port or inject a library. Re-sign it with the team's Developer ID, hardened runtime, JIT only, and an identifier different from the app's.
    - **Every Mach-O.** Team-signed, with hardened runtime and no `get-task-allow`. Native addons are team-signed, so library validation admits only the team's code.
    - **Main.** It refuses `remote-debugging-*`, `inspect*` and `js-flags` before anything else; hardened runtime doesn't stop CDP. The fuses stay.
    - **Every companion process.** It runs with `--disable-sigusr1`; hardened runtime doesn't stop that either. The CLI line and MCP configuration the GUI hands to agent hosts start with it.
    - **Engine (SEA).** Built from the official Node with `postject` (Node 24 has no `--build-sea`), re-signed with the team's Developer ID under its own identifier, hardened runtime, `allow-jit` only (it crashes at start without it). The SEA config needs `"execArgvExtension": "none"`: a default SEA runs code from `NODE_OPTIONS`. It also needs `"execArgv": ["--disable-sigusr1"]`. Command-line Node options are only arguments to a SEA. Native addons (identity, keychain, better-sqlite3) load only in the Engine, only from beside its executable, and only team-signed.
    - **Engine environment.** A SEA still honors `NODE_TLS_REJECT_UNAUTHORIZED`, `NODE_EXTRA_CA_CERTS` and `NODE_USE_ENV_PROXY`, and anyone can start the real Engine. So its first act is to compare `process.env` with an allowlist and exit on anything else. The list holds `HOME`, `TMPDIR`, `USER`, `LOGNAME`, `LANG` and `LC_ALL`, plus `__CF_USER_TEXT_ENCODING`, which CoreFoundation adds to every process. It also holds the Draft Tide variables a release build honors: `DRAFT_TIDE_DATA_DIR` and `DRAFT_TIDE_ENGINE_IDLE_MS` (the development knobs and `PATH` are refused, not ignored). Release builds only: `src/engine/env-guard.ts`, imported first; a development Engine runs with whatever its tests give it. Launchers already build its environment from scratch (engine-client's `engineEnvironment`).
  - **Per build.**
    - **Release.** The requirement is compiled into the Engine bundle (`apps/companion/scripts/build.ts`). No environment variable, argument or file can set or relax it. Without the addon, or off macOS, a release Engine refuses every desktop connection rather than check less.
    - **Development.** The signature check is skipped, and `engine.info` reports `desktopIdentity: "development"`. On macOS the instance is still pinned through the addon.
    - **E2E.** Only the E2E desktop build (`dist-e2e/`) lets Main accept debugging switches, for Playwright. It is never shipped.
  - **Engine identity.** Under the SEA the desktop can check the Engine socket's peer the same way: the SEA Engine satisfies the Engine requirement, and a script on the companion Node doesn't (token-custody D1).
  - **The Preview Host (release).** Its own executable, `Contents/MacOS/Draft Tide Preview`: a copy of the app's Electron stub signed with its own identifier (`….preview-host`, JIT only), so it fails the desktop requirement and a page that escaped the renderer's sandbox can't pass for the desktop. It lives beside the app's executable because Electron resolves its framework, helpers and `app.asar` from the executable's bundle and checks the asar's integrity only inside it; a nested helper app doesn't work (M1-09 record). Main picks the role by executable in a release: the app's executable refuses `--dt-preview-host`, the Preview Host's runs nothing else. A renamed copy of the app's executable is killed at launch, so only the app's own executable carries the desktop identity.
  - **Open.** Windows is unverified.
- **Where truth lives.** The project's own Git repo (the project folder's `.git`) owns history and raw bytes. It is a *design repo*: Draft Tide manages it, engineers only read it. Every snapshot is a full-tree commit on the checked-out branch, and metadata goes in canonical JSON inside the commit message. Project identity and settings (projectId, entry files, extra excludes) live in `.drafttide.json` at the repo root, inside the tree, and are **untrusted input** (strict schema, `CONFIG_INVALID` on anything unsafe). SQLite owns local bindings, remote bindings, plans, the agent-access setting, the operation journal and the sync queue; it is **not a cache**. Only the history index, diffs, preview metadata (the `preview_cache` table) and the preview PNGs (`projects/<id>/cache/previews/`) are rebuildable. No LFS, no second asset store, and no second copy of history (no app-data bare repo, no backup container).
- **Draft Tide manages the design repo, within limits.** It may change only: the checked-out branch's ref (compare-and-swap on the expected old OID), the index (under `index.lock`), planned working files, `.drafttide.json`, temp index files and objects inside `.git`, and `refs/remotes/draft-tide/*`; `remote.origin.*` only after the user confirms connecting a remote. It never rewrites history (no rebase, reset or force-push), never calls the porcelain commands checkout, stash, clean, merge, add, commit, status or diff (plumbing only, e.g. commit-tree), never runs the repo's hooks, filters, textconv or configured programs, never signs, and leaves the user's other branches, tags, stash, config and hooks alone. It refuses repo forms it cannot handle safely (shallow, linked worktree, submodule, LFS, detached HEAD, merge or rebase in progress, `text`/`eol` attributes on files with CR…) before writing anything.
- **Git hygiene.** Git goes through named backend operations (hash-object `--no-filters`, temp index, write-tree, commit-tree, update-ref with expected-old-OID, ls-files, check-attr, merge-base, fetch/push…). Calls use spawn with argument arrays, explicit `--git-dir`/`--work-tree` and a from-scratch env (with `GIT_GRAFT_FILE=/dev/null`: grafts survive `--no-replace-objects`). **Local operations** override the repo's config on the command line (hooks path, fsmonitor, attributes/excludes files, autocrlf, signing, auto gc, UTF-8 commit encoding, `protectHFS`/`protectNTFS` on every platform…). **Network operations never read the project's Git config**: a repo's `url.*.insteadOf` or `http.proxy` can redirect traffic and steal the token, and multi-valued keys cannot be cancelled with `-c`. They run in an ephemeral empty git dir with `GIT_OBJECT_DIRECTORY` pointing at the project's objects, `GIT_ALLOW_PROTOCOL=https`, and credentials through a 0600 askpass file. The bundled Git must be a full build with `git-remote-https` (M0's trimmed build has none). What ships is a subset of dugite-native 2.53.0: `bin/git` and `libexec/git-core/git-remote-https`, plus the symlinks `libexec/git-core/git` and `git-remote-http`; no GCM, git-lfs, scalar, templates or dugite's `etc/gitconfig`. On macOS arm64 that is 5.1 MiB (2.6 MiB as tar.gz), against 148 MiB for the full build. Both links only system libraries, so TLS uses the system's libcurl and trust and no CA bundle ships; only these two Mach-Os need team signing. The build doesn't derive its exec path (`--exec-path` says `//libexec/git-core`), so the Engine must set `GIT_EXEC_PATH` for the bundled Git, or `git-remote-https` isn't found. In development the Engine detects it (`detectExecPath`): null for a system Git, `<prefix>/libexec/git-core` for a Git laid out like dugite's. macOS x64, Windows and Linux are not measured. No passthrough, no arbitrary revision expressions.
- **Agent access is consent; there are no approvals.** One global switch in the trusted GUI, off by default. When it's on, CLI and MCP (treated the same) may operate on every bound project without per-operation confirmation. With it off, the tool channel gets only `engine.info` and the handshake; everything else returns `AGENT_ACCESS_DISABLED`.
  - **Agent-runnable when on.** Local, recoverable operations: query, save, compare, restore, pull (fast-forward only), recovery apply, and open-from-remote into a missing or empty folder. Anything that writes working files stays plan → apply, and apply re-checks access, HEAD and the fingerprint (`PLAN_STALE`).
  - **GUI-only.** Binding a new folder (scope review), GitHub sign-in, connecting a remote and the first push. The tool channel can only *request* these (`CONFIRMATION_REQUIRED` plus an operationId; a user decline is `APPROVAL_DENIED`), and `--yes`, `--force` or `confirmed: true` never count. For a folder (`project.connectRequest`) the Engine records the path without touching it; the app shows the request, the user picks the folder in the native picker and binds it with `requestId`. At most 20 requests wait. Recording one brings the app forward (`request.waiting`) or starts it: a release Engine opens the app bundle it ships in, found from its own place. `details.app` says `shown`, `opening` or `unavailable`. Opening the app answers nothing.
  - **Checked three times for applies.** In the policy, again under the project's write guard, and again before the first working file is written. After that the operation finishes or stops for recovery.
  - **A folder is granted by the native picker.** Main lets `project.review` and `project.bind` through only for a folder the user picked in the dialog during this run (`INVALID_ARGUMENT`, `folder-not-chosen`). Bind reviews again and compares the review token (`SCOPE_CHANGED`), refuses everything that would stop the first save before writing, then runs `git init` (if needed), writes `.drafttide.json` compare-and-swap on the reviewed bytes, and records the binding. A settings file naming a project bound to another folder that still holds it is `PROJECT_ALREADY_BOUND` unless the user connects it as a new project; a folder whose old location is gone relinks.
  - **Visibility.** Agent restores and pulls show up as GUI notices and carry their source in history.
  - **Accepted risk.** A misled agent can restore without asking. Protection versions keep the data. There are no approval receipts or approve actions.
  - **Sync.** After the user authorizes syncing a project, background pushes need nothing further (they write no working files).
- **Restore appends history, and publishing is lock-first.** A restore adds a pre-restore protection commit (only when the folder has unsaved changes) and a restore commit; it never rewinds HEAD. Operations move through `planned → confirmed → preflight → protected → staged → applying → verified → publishing → committed → completed` (or `recovery-required`); requests wait in `awaiting-user`; other ends are `failed`, `cancelled`, `superseded`, `denied`, `rolled-back`. `publishing` means: take `.git/index.lock` (fail with `LOCKED` before changing anything), compare-and-swap the ref, atomically rename the prebuilt index in, release the lock. Moving the ref first would leave a stale index in which someone else's plain `git commit` silently re-commits the old tree (measured in the spike). Before taking the lock, publish checks that the prepared index describes the commit's tree; under the lock it checks that HEAD is still on that branch (`HISTORY_CHANGED`, `branch-changed`); after the ref moved, or when the ref can't be read back, a failure keeps the lock (`RECOVERY_REQUIRED`). A failed compare-and-swap is classified from the repo's state (`HISTORY_CHANGED`, `LOCKED`), never from Git's wording.
- **The journal and recovery (M1-05).**
  - **The journal.** SQLite's `operations`, `operation_files` and `plans`. Every step is written before it happens, compare-and-set on the state the caller saw, through core's transition table; saves are journaled too, and a publish's intent (ref, expected old, commit, tree) is recorded before the lock. Rows are read back strictly (`STORAGE_IO_FAILED`, `corrupt-record`). Ended rows are kept 30 days; unfinished ones never go.
  - **Plans.** Stored, valid 30 minutes, applied once (consuming the plan and starting the operation are one transaction). The apply recomputes the fingerprint from its own stable capture, the same capture that becomes the protection version (`PLAN_STALE` with a reason otherwise). A plan id is never authorization; unknown or other projects' plans are `INVALID_ARGUMENT`.
  - **Restore writes.** Deletes first, then writes (rollback undoes in reverse); each file only while it still holds what the capture saw (or nothing), via an exclusive `.restore.dt-tmp-<uuid>` beside it whose content id is checked, flushed, then renamed (Windows retries check again first). Names are matched by exact spelling, never by what a case-insensitive filesystem resolves them to, so a case-only rename works. Real-folder parents only. Nothing outside the scope is ever written or deleted; anything in the way that no version holds is `UNTRACKED_FILES`. The version's `.drafttide.json` comes back only if it names this project. After the first file the operation finishes or goes to `recovery-required`, never rolled back silently.
  - **Recovery.** At Engine start and under the write guard before every save or restore. Completed without asking: operations that wrote no working file, and index switches whose ref moved. Left to the user (`recovery.plan` / `apply`, finish or rollback): a restore that wrote files; both only move files that still hold the expected content and leave conflicts as they are. A Draft Tide lock with no journal row counts as an index switch only if the tip's metadata carries its operationId; otherwise the user may remove it. Only Draft Tide's own locks are ever removed, never by age.
  - **Cancel.** At safe boundaries only (`CANCELLED`): a save until it publishes, a restore until its first file.
- **Capture and scope.**
  - **Capture.** Every file is hashed, then free space is checked for exactly the new content, which streams into immutable staging outside the folder. A full rescan checks stability (up to 3 retries before `SOURCE_BUSY`).
  - **Objects.** Git objects come only from staged bytes, or from blobs the index already references under any path, so renames and copies are free (never a dangling object), and an unchanged tree returns `NO_CHANGES`. Capture writes nothing into the folder or its `.git`.
  - **The tree.** It is built in `.git/index.dt-<operationId>` and checked against the intended entries: `update-index` skips a path it refuses with exit code 0, and a version must never silently lose a file. Names any filesystem would take for `.git` (any case, HFS+ ignorable characters, `git~1`, trailing dots or spaces) are refused in the scope (`isSafeRelativePath`).
  - **Scope.** It follows `git add -A` semantics: tracked files are always in; new files are in unless `.gitignore`, `info/exclude`, the default excludes (secrets, caches…) or the project's excludes drop them, and excludes never remove a tracked file; `.drafttide.json` is always in. Anything in scope that can't be saved is reported, never skipped.
  - **Paths.** Every path Git hands over has its parent directories checked (an index path can run through a symlink to outside the project), and a file must still be the inode the scan saw when it is opened.
  - **Reasons.** Refusals carry the stable reasons defined in `contracts/src/scope.ts`.
- **Remote sync is local-first and fast-forward only.** Saving never waits for the network; push and pull are separate operations. A connected project syncs the branch recorded at connect time (not HEAD); a save, restore or recovery queues a background push (`sync_queue`), which runs under the project's sync guard, never its write guard, and retries `NETWORK_UNAVAILABLE` with backoff, waits for a sign-in on `AUTH_REQUIRED` and for the user on `REMOTE_DIVERGED`/`REMOTE_REJECTED`; the Engine stays up while a push is due. A pull is plan → apply like a restore (refused with `UNSAVED_CHANGES`, fast-forward published lock-first, no new commit); opening from GitHub takes only repositories the app is installed on, never into hidden folders or `~/Library` (an agent may open too), and binds the project before its first file, so recovery covers it (finish only; anything stopped before the first file is undone). No `+` refspec, no force-push: if both sides have new versions the result is `REMOTE_DIVERGED` and nothing changes on either side. GitHub sign-in is skippable and happens only in the trusted GUI. The token lives only in the Engine (OS keychain) and never appears in argv, `.git`, SQLite plaintext, logs, the diagnostics report, commit metadata, the tool channel or the Preview Host. **Draft Tide doesn't create repos in M1** (decided 2026-10-02): the GUI guides the user to create an empty repo on GitHub themselves (private recommended; no README, `.gitignore` or license), then connects it. The Engine checks push access and reads the repo's visibility; the first push into the empty repo is the project's branch, which then becomes the default (GitHub won't delete a default branch). A non-empty repo with no common ancestor is `REMOTE_DIVERGED` (`unrelated-history`), nothing changed. The user also installs Draft Tide's GitHub App on that repo, and the GUI lists the app's installed repos to pick from; push access is checked against that list, not the repo's `permissions` field (that is the user's own role). An app no longer installed is `REMOTE_REJECTED` (`app-not-installed`), not `AUTH_REQUIRED`.
- **GitHub sign-in (decided 2026-10-02).** A GitHub App with only Contents read/write and Metadata read, Device Flow on, expiring user tokens. The client ID is public and compiled in; the app never holds a client secret or private key. The dev app is `draft-tide-dev-lutas2000` (installable on its owner's account only); the release app is `draft-tide` (client ID `Iv23li5bVjuyY8pVqtz5`, public, installable on any account; created 2026-10-03), compiled into release builds. User tokens (`ghu_`) last 8 hours, refresh tokens (`ghr_`) about 6 months, and every refresh voids the old access and refresh tokens. So the Engine runs one refresh at a time, writes the new refresh token to the keychain before using the new access token, and refreshes before a Git network operation, never during one. Git gets the token with the username `x-access-token`. Signing out deletes the local token; revoking on GitHub is the user's step in GitHub's settings.
- **Token custody (decided 2026-10-03).** The token lives in the login keychain, in an item the Engine creates in-process through its addon (`apps/companion/native/keychain.c`; one item per data store: service `app.drafttide.github`, `dev.drafttide.github` in development, account = the store's id in SQLite). Core never holds it: `RemoteProvider` (remote-github) owns it, and a Git network operation gets an opaque credential only git-backend reveals into its askpass file. Development builds on macOS use the same item, which then trusts the development Node; elsewhere, and with the test GitHub, a memory vault. It never goes through `/usr/bin/security`, which would make `security` the trusted reader. The item's default access list trusts only the Engine's designated requirement: identifier, Developer ID markers and team. A new Engine build signed the same way reads it with no dialog. A script on the companion Node, the official Node or a forged ad-hoc SEA gets `errSecAuthFailed`. Reads never allow UI. The Engine sends the token only to `https://github.com` and `https://api.github.com`, checked before each request, because a remote binding in the writable data store could name another host. Residual: a process that allows UI makes macOS ask the user, and "Always Allow" trusts it for good. Before the first push the GUI shows what will be pushed and the repo's visibility (a public repo gets a clear warning); pushed history cannot be taken back by the tool.
- **Commit identity.** The signed-in GitHub user's display name with their `ID+USERNAME@users.noreply.github.com` address; before sign-in a fixed "Draft Tide" identity; never the private email or the global Git identity. `CommitIdentity` refuses names Git would silently rewrite (`<`, `>`, line breaks, leading or trailing punctuation), so GitHub names must be normalized first; with no display name set, use the login. Commit times are whole seconds in UTC. Draft Tide's commits run no hooks and are unsigned (accepted): an engineer's pre-commit formatter does not apply to saves, and a remote rule that requires signatures makes the push fail with `REMOTE_REJECTED`.
- **No fixed quotas.** Don't cap project size, file size, file count or version count. Use bounded streams, disk-space preflight, progress and recoverable errors. Diff and preview budgets must never exclude original files from a save. A remote's limits (GitHub blocks files over 100 MiB) only affect pushing and never block saving.
- **Preview isolation (M1-06).**
  - **Supervised by the Engine.** The Engine starts the Preview Host with `--dt-preview-host` (in a release its own executable, see "Desktop identity"; in development the app binary; one host per project, reused, stopped when idle) with an inherited pipe (fd 3), a fresh scratch directory and an environment built from scratch: no data directory, database, Git, tokens or Engine channel. A failed preview never undoes or changes a save, and is never cached.
  - **Served from Git, on request.** Every `dt-preview://job/<path>` the page asks for goes over the pipe; core decodes it once, accepts only a safe relative path, and serves only regular files of that version's tree, of an allowed type, within per-file, per-render and request budgets. Everything else is recorded as missing. Previews never read the folder or write to it or its `.git`; what is shown is a version, never unsaved state.
  - **The renderer.** Offscreen, sandboxed, context-isolated, no Node or preload, an in-memory session per job, software rendering, dialogs off, fixed 1280×800 (`en-US`, the computer's time zone, animations jumped to their end). Scripts run: connecting the folder is the trust decision. The network is closed below the page (request filter allowing only `dt-preview:`, `data:`, `blob:`; DNS mapped to nothing; WebRTC forced through a dead proxy; permissions, downloads, popups and navigation refused), so blocked attempts are recorded instead of vanishing in a CSP check.
  - **What crosses the boundary.** Images are checked (PNG/JPEG header, pixel budget) before the sandbox decodes them, and the host's PNGs must have exactly the requested sizes. Callers get an artifact (bound to the project, 30 minutes, read in base64 chunks by `preview.read`), never a path. Page text (missing paths, blocked URLs) is made printable and sampled. Screenshots live only in the local rebuildable cache, never in the design repo.
  - **Later.** Capture control (viewport emulation, full-page shots, M2) uses in-process CDP through `webContents.debugger` inside the Preview Host, never a remote-debugging port; Playwright is a dev/CI tool only.
  - **Its own identity in a release (M1-09).** The Preview Host ships as a separately signed executable with its own identifier, outside the desktop requirement (see "Desktop identity"), and the release checks render a page through it under the Engine's supervisor (R4, R5).
- **Machine output.** CLI and MCP stdout carry protocol data only; diagnostics go to stderr. Use the JSON envelope `{schemaVersion, ok, data, warnings, error{code,message,details,retryable}}`, with stable error codes defined once in `contracts` (see M1 plan §11.1). With `--json` the CLI prints exactly one envelope line.
  - **Exit codes** come from the envelope: 0 ok, 1 failed, 2 usage (`INVALID_ARGUMENT`), 3 no-op (`NO_CHANGES`).
  - **MCP `isError`** is set for failures but not for a no-op. MCP tools are generated from the catalog (`snake_case` names); the host validates arguments loosely so unknown fields reach the Engine's strict schema; `snapshot_preview` adds the PNG as image content after the envelope, read in chunks and checked against the artifact's hash (a picture that can't be attached is a warning, not a failure).
  - **Non-`DtError` exceptions** surface as `INTERNAL_ERROR`.
- **History and comparison.** Versions are resolved and numbered along the checked-out branch's first-parent line. A reference is a snapshot id or a full commit id on that line, never a revision expression (`SNAPSHOT_NOT_FOUND` for an id not on it). The oldest commit carrying a snapshot id is the version; a later one is another tool's copy. Which files changed comes from tree and blob ids; the line view (jsdiff) and every list that crosses the process boundary have budgets and say `truncated`, never limiting what is saved. Text from Git (titles, other tools' author names) is made printable before it leaves the Engine; other tools' emails don't leave it. Status compares the folder with the newest commit, with a display-only hash cache; saving never uses it.
- **Commit metadata** must never include absolute paths, prompts, keys, the GitHub token or Engine connection tokens. The only personal data is the display name and noreply address of the commit identity. It is the message's last line, `Draft-Tide-Snapshot: <canonical JSON>`, after a blank line (`contracts/src/snapshot.ts`). Reading it back is strict, because messages are untrusted: canonical JSON only, at most 4 KiB, the schema exactly; anything else is an external commit or unreadable.

## Product rules that shape code

- Every user-facing feature needs a GUI path; no CLI-only or agent-only features. Manual use must work offline without an agent, account or API key.
- GUI copy uses designer terms such as "保存版本" (save version) and "回復到此版" (restore this version). Show snapshot UUIDs and Git OIDs only in details or diagnostics. Show a completed restore only after the Engine reports verified or completed state, not optimistically.
- M1 scope: generic filesystem source, a single line (the checked-out branch, `main` for new projects), manual saves only, previews of self-contained HTML/CSS/JS plus PNG/JPEG (entry page side by side at a fixed viewport), and skippable GitHub sign-in with fast-forward-only sync and open-from-remote. M2 brings branches/directions, autosave, and per-page visual comparison. That comparison ranks pages > DOM regions > images > line diff and uses viewport presets from `.drafttide.json`. It renders only the pages a change affects, found through a per-page dependency map (ROADMAP §7.2, TECH_STACK §10.4). Don't build any of it in M1. Source adapters come in M3; multi-designer collaboration (divergence handling, review) in M4. Engineers are read-only users of the design repo; there is no application-repo handoff and no backup/import.
